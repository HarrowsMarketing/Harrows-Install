# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Harrows Install EOD — end-of-day install reporting tool for the Install/CS team, replicating a Base44 prototype ("Harrows ReportHub") Morgan built. Standalone sibling repo to the main Harrows Marketing dashboard (`C:/Users/rockyj/Harrows-dashboard`), deliberately not folded into it — different audience (install crews, not marketing/sales) and different release cadence.

**Live URL:** https://installs.harrows.co.nz
**GitHub:** https://github.com/HarrowsMarketing/Harrows-Install
**Deploy:** Vercel, auto-deploy on push to `main`. Git identity for this repo is `HarrowsMarketing` / `marketing@harrows.co.nz` — pushes from any other identity won't trigger a deploy (check `git config user.email` before pushing, same convention as the main dashboard).
**Dev servers:** `npm run dev` (Vite, frontend) + `npm run server` (Express API on port 3001, proxied via `vite.config.ts`) — run both.

## Commands

```
npm run dev       # Vite dev server (frontend only)
npm run server    # local Express API (api/index.js via dev-server.js), port 3001
npm run build     # tsc -b && vite build
npm run preview   # serve the production build locally
node gen-icons.cjs # regenerate PWA icons from public/Harrows_Icon_Hardhat.png
```

No test suite exists in this repo yet (no `test` script, no test framework installed).

## Architecture

Same overall shape as the main dashboard: a single Express app (`api/index.js`) handling every `/api/*` route, deployed as one Vercel serverless function per `vercel.json`; a Vite/React SPA frontend; Supabase (raw PostgREST via axios, no SDK) for data; Vercel Blob for file storage. `dev-server.js` is the local-only entrypoint that wraps `api/index.js` in a plain `app.listen` — Vercel itself imports `api/index.js` directly as the function handler.

**Auth is hybrid, and it's the main thing to understand before touching any route:**
- **Office/admin shell** (`/`, `AppRoot.tsx` → `AdminShell.tsx`) reuses the *same Clerk instance* as the main Harrows-dashboard, so office staff sign in with their existing account. Requires `install` in their Clerk `publicMetadata.allowedDepts` (or `role: admin`/`super_admin`). Enforced by `requireDept('install')` (aliased as `requireAdmin` in `api/index.js`).
- **Field installers** (`/report`, `InstallerApp.tsx`) never touch Clerk at all — `AppRoot.tsx` has an explicit escape hatch checking `path === '/report'` before ever rendering `<SignedIn>`/`<SignedOut>`. They log in with a 6-digit PIN (`POST /api/install/pin-login`) against the `installers` table, getting back a short-lived HMAC-signed session token (signed with `INSTALLER_SESSION_SECRET`, stored in `localStorage` via `utils/installerSession.ts`) — this is a custom token, not a Clerk JWT.
- `requireInstallerOrAdmin` accepts either token type on the same route; `requireInstallerSession` accepts installer-only; `requireAdmin` accepts Clerk-only. An installer's `admin_access` flag (separate from Clerk's admin role) lets them see all reports/jobs through the PIN flow instead of just their own.
- **`src/lib/api.ts`'s axios interceptor** auto-attaches whichever token is present (installer token takes priority) to any request whose URL starts with `/api`. **This interceptor is axios-specific** — anything that makes its own `fetch()` calls outside axios (see Blob upload gotcha below) needs the token attached manually via the exported `getAuthHeaders()`.

**Data model** (Supabase, tables created by `supabase_eod_migration.sql` + `supabase_job_card_fields_migration.sql` + `supabase_installer_profile_migration.sql`): `installers` (PIN roster — `name`/`phone`/`photo_pathname` are installer-editable via their own profile, `pin`/`role`/`admin_access` are admin-only via the People tab), `job_cards` (job number/project/address + billing/PM/salesperson contact fields), `eod_reports`, `eod_report_photos` (pathnames only, actual bytes in Vercel Blob), `eod_config` (generic key-value settings), `eod_signin_log` (still recorded on every PIN login, but no longer surfaced anywhere in the UI — see Activity tab below).

**Installer self-service profile:** any installer (PIN session, admin_access or not — this is orthogonal to that flag) can edit their own `name`/`phone`/`photo_pathname` via `MyProfileModal.tsx` (entry point: "My Profile" link in `InstallerApp.tsx`'s header), through `GET`/`PATCH /api/install/me` (`requireInstallerSession`). Office/Clerk staff were deliberately **not** given an equivalent — Clerk's own "Manage account" portal already covers name/photo for them, and there was no ask to duplicate that. The phone field is labelled "Work phone / contact number" specifically so installers know admins can see it (surfaced in the People tab as plain text + a small avatar next to each name) — there's no separate audit/history log of profile edits, just the current value.

**Env vars** (`.env.example` has the full list): `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (own Supabase project, intentionally separate from the main dashboard's — different data sensitivity), `BLOB_READ_WRITE_TOKEN`, `CLERK_SECRET_KEY` + `VITE_CLERK_PUBLISHABLE_KEY` (shared with main dashboard, same Clerk instance), `INSTALLER_SESSION_SECRET`, `APP_ORIGIN`, `ANTHROPIC_API_KEY` (Claude API — see below), `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`EMAIL_FROM` (report-submission notification emails — see below; same Office365/nodemailer pattern as `harrows-dashboard/api/sales/daily-email.js`, but a distinct SMTP config since this is a separate Vercel project). Unlike the main dashboard, `.env` is correctly gitignored here — no known secret-in-git-history issue on this repo.

**Report notifications, editing, and the client-facing notice (added 2026-08-10):**
- `PATCH /api/install/reports/:id` lets an installer edit a report they filed themselves (`requireInstallerOrAdmin`, checked against `installer_id`) or a Clerk admin edit any report — but never once `email_sent` is true; the route 403s outright rather than un-processing it, since the client may have already received the old version. Photo edits are reconciled as a diff against `eod_report_photos` (delete removed pathnames, insert new ones), not a wholesale replace.
- `eod_config` key `notification_recipients` (`{name, email}[]`, editable in Settings) drives an email fired from `POST /api/install/reports` on every new report — deliberately opt-in, nobody gets it by default. A second, separate source feeds the same send: `eod_config` key `admin_notification_optins` (`{[clerkUserId]: {name, email, enabled, updatedAt}}`), toggled by each Clerk admin themselves via `GET`/`PATCH /api/install/my-notification-pref` ("My notifications" in Settings) — self-service and off by default, distinct from the shared recipients list any admin can edit for anyone else. `sendReportNotification` unions both lists (de-duped) before sending. Send failures are caught and logged, never surfaced to the submitting installer/admin or allowed to fail the report submission.
- The defects/damages notice (`defectsNoticeText`) moved from a tiny per-page PDF footer to a bold, rule-bracketed block in normal document flow, positioned right before the "End of day photos" section on both the PDF and the on-screen `ReportDetailModal` — so it's read before the photos, not after every page.

**Activity tab** (`ActivityTab.tsx`, admin-only) shows recently-created job cards and filed reports, merged and sorted by `created_at` — it does *not* query `eod_signin_log` (that was the original version and got noisy/low-signal fast). It just re-fetches the existing `/api/install/jobs` and `/api/install/reports` list endpoints and merges client-side rather than having its own backend route. `job_cards.created_by` is a free-text snapshot taken at creation time (installer name, or the Clerk user's display name — see `clerkDisplayName()` — falling back to `null`, never the raw Clerk user ID), so it stays correct even if that person is later renamed or removed.

## Job card scan-to-autofill (Claude API)

`POST /api/install/jobs/scan` sends a photo/PDF of a physical job card to Claude (`@anthropic-ai/sdk`, model `claude-opus-4-8`) and gets back structured JSON to pre-fill the add/edit form (`src/components/JobCardModal.tsx`) — nothing is saved until the user reviews and hits save. Uses `output_config.format` with a `json_schema` for structured extraction (not tool-use). Requires its own `ANTHROPIC_API_KEY` from console.anthropic.com — this is not shared with any other Harrows service and needs its own billing set up.

## Gotchas (found the hard way this session — not obvious from reading the code alone)

- **Debugging pattern for "it works locally but not on Vercel" issues:** add a temporary unauthenticated route like `app.get('/api/_debug_x', ...)` that calls the suspect function directly and returns what actually happened (env var presence, raw error message, etc.), push, `curl` it, diagnose, then delete it before the next real commit. Found two real bugs this way: `SUPABASE_URL` had `/rest/v1/` mistakenly appended (copied from Supabase's newer "Data API" settings page instead of the bare project URL → `PGRST125` double-path error), and confirmed `BLOB_READ_WRITE_TOKEN` was fine when a photo-upload bug was actually elsewhere.
- **Supabase's newer key system:** the dashboard now shows "Publishable"/"Secret" keys by default instead of "anon"/"service_role". This app's raw-PostgREST code needs the **legacy `service_role`** key specifically (under the "Legacy anon, service_role API keys" tab) — PostgREST decodes a JWT `role` claim, and the new opaque `sb_secret_...` format isn't that.
- **Cloudflare + Vercel domain setup:** adding `installs.harrows.co.nz` as a Cloudflare-proxied (orange cloud) record from the start causes a 308 redirect loop, because Vercel can't complete its one-time domain-ownership verification/cert issuance through the proxy. Fix: set the DNS record to "DNS only" (grey cloud) until Vercel shows "Valid Configuration" for the domain, *then* switch it back to "Proxied". Don't touch the zone's SSL/TLS mode ("Flexible") — other non-Vercel records on the zone may depend on it; scope any future SSL fix to a Configuration Rule for the specific hostname instead.
- **`@vercel/blob/client`'s `upload()` makes its own `fetch()` calls** — it does not go through the app's axios instance, so the axios auth interceptor never attaches a token to its `handleUploadUrl` request (`/api/install/photos/upload-token`). Must pass `headers: await getAuthHeaders()` explicitly (see `src/components/PhotoUpload.tsx`), or the token endpoint 401s and the client library reports a vague "failed to receive the client token".
- **Live `FileList` + async ordering:** file input handlers here follow the pattern `onChange={e => { handleFiles(e.target.files); e.target.value = '' }}`. `e.target.files` is a *live* reference. If `handleFiles` has any `await` before it snapshots the files (e.g. `Array.from(files)`), the synchronous `e.target.value = ''` on the next line clears the live list during that yield — silently uploading zero files with no error. Always snapshot `Array.from(files)` as the very first synchronous statement in the handler, before any `await`. Bit us once already in `PhotoUpload.tsx` when an auth-header fetch was added before the snapshot.
- **Phone camera photos are resized client-side before upload** (both `JobCardModal.tsx`'s scan and `PhotoUpload.tsx`'s report photos) — via canvas, max long edge ~1600-2000px, re-encoded to JPEG at ~0.85 quality. Real camera photos are routinely 5-10MB+ and sometimes HEIC; without this, large multipart uploads fail outright on mobile connections ("Failed to fetch"), and the canvas re-encode incidentally sidesteps HEIC compatibility since it always outputs JPEG regardless of source format.
- **`mailto:` links can never carry attachments** — hard browser/OS limitation. The "email the report" flow (`shareOrDraftReportEmail` in `src/utils/emailDraft.ts`) generates a real PDF and hands it to the Web Share API (`navigator.share({ files: [...] })`) so it actually attaches via the native share sheet on phones. Falls back to downloading the PDF + a text-only `mailto:` draft on desktop browsers without file-sharing support.
- **`jsPDF`'s `doc.addImage(data, format, x, y, w, h)` stretches to the exact `w`/`h` given — it does not preserve aspect ratio.** Any photo added to a PDF (`src/utils/generateReportPDF.ts`) must compute the fit itself via `doc.getImageProperties(imgData)` and scale to a max box, or it comes out visibly squished.
- **PWA icons don't auto-refresh on phones once installed.** `manifest.json`'s icon `src` values and `index.html`'s `<link rel="apple-touch-icon">`/`<link rel="icon">` hrefs carry a manually-bumped `?v=N` — bump it in both files together whenever `gen-icons.cjs` regenerates the PNGs, or devices keep showing the stale icon even after removing and reinstalling. `gen-icons.cjs` also centers the icon on the H shape's own bounding box specifically (computed from the plain no-hat master logo as a geometric reference), not the combined H+hardhat bounding box — centering on the combined box visually skews the H off-center since the hat hangs off to the right.
- Installer PINs must be exactly 6 digits — enforced both client-side (`PeopleTab.tsx`) and server-side (`isValidPin` in `api/index.js`, on both create and update). This was added mid-development, not an original constraint.
- **Circular avatars in the PDF are cropped on a `<canvas>` client-side, not via jsPDF's own clip API** (`circularAvatarDataUrl` in `generateReportPDF.ts`). jsPDF *does* support path clipping (`saveGraphicsState()`/`circle()`/`clip()`/`discardPath()`), but the canvas approach was chosen instead — same technique the codebase already uses for photo resizing (`resizeImage.ts`), and it just hands `addImage()` a plain PNG with transparent corners, no PDF-level clip/restore bookkeeping to get wrong.
- **Any report object built by hand in the frontend instead of fetched from `GET /api/install/reports[/:id]` silently drops joined fields it doesn't explicitly copy.** Bit us once already: `NewReportForm.tsx`'s post-submit share flow constructs its own `installer: { id, name }` object (the raw insert response from `POST /api/install/reports` only has `installer_id`, not the joined row) — it originally didn't copy `photo_pathname`, so the installer's avatar was silently missing from the PDF on that one path even though it worked correctly everywhere else (My Reports, admin Library) since those always fetch through `REPORT_SELECT`. Whenever `EodReport`/`Installer`/`JobCard` gains a new field, grep for other spots that hand-build one of these shapes instead of fetching it.
